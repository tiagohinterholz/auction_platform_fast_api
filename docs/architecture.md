# Architecture

## Style

**Modular monolith, event-driven, domain-oriented.** Single deployable (`api` + `worker`), clear
module boundaries enforced by convention (no module imports another module's internal models),
internal communication via domain events instead of direct cross-module calls where a *reaction*
(not a query) is what's needed. See `docs/bounded-contexts.md` for the reasoning behind that
choice and what it costs/saves compared to real microservices.

## System overview

```
[ Client ]
    | HTTP / WebSocket
[ FastAPI api ]  ---publish--->  [ RabbitMQ ]  ---consume--->  [ FastAPI api ]
    |                                  ^                            |
    | Celery (schedule)                | publish                   WebSocket
    v                                  |                            v
[ Celery worker ] ------------------- (start/finish tasks) ---> [ Client ]
    |
[ PostgreSQL ]   [ Redis (locks + Celery broker) ]
```

The `api` and `worker` are **separate processes**, each connecting independently to Postgres,
Redis, and RabbitMQ. Domain events (`AuctionCreatedEvent`, `BidPlacedEvent`, ...) are how a
change in one place (e.g. the worker finishing an auction) reaches code that reacts to it
elsewhere (e.g. the API process pushing a WebSocket message) — see `docs/domain-events.md`.

## Module layout

```
app/
├─ modules/
│  ├─ auction/       domain / application / infrastructure / routers
│  ├─ bidding/
│  ├─ users/
│  ├─ auth/
│  └─ notifications/
└─ core/              cross-cutting infrastructure, no domain logic
   ├─ database/  events/  locks/  celery/  auth/  security/
   ├─ email/     sentry/  logging/  redis/  websockets/
```

Rules:
- A module never imports another module's domain entities directly.
- Cross-module *queries* ("what's the current state of X") go through the owning module's
  repository **interface** (hexagonal port), never its concrete implementation or raw tables.
- Cross-module *reactions* ("something happened, react if you care") go through domain events.

## Database

PostgreSQL, single physical database, **CQRS-lite** per context: a write model (the aggregate's
own table) and a denormalized read model, kept in sync by an event handler.
```
auctions       (write)      auctions_read   (read)
bids_history   (write/read combined for bidding)
```
No foreign keys or joins across contexts. Ownership is enforced by convention (see
`docs/bounded-contexts.md`), not by the database.

## Concurrency

- **Redis distributed lock** per auction (`auction:{auction_id}`) guarantees only one bid wins a
  race for the highest-bid slot.
- Atomic state transitions, idempotent writes where retried (refresh token revocation, planned:
  payment webhooks).

## Async processing

- **Celery + Redis** — real task queue (survives restarts, distributed) for time-based auction
  transitions: `start_auction_task`, `finish_auction_task`, scheduled with a countdown when an
  auction is scheduled.
- **RabbitMQ** — domain event bus between processes (`app/core/events/rabbitmq_event_bus.py`,
  `aio-pika`). Swappable for an in-memory bus (`EVENT_BUS_PROVIDER=memory`, the default, and what
  the test suite always uses) via the same `EventBusInterface` — no use case or handler needs to
  know which one is behind it.

## Real-time communication

FastAPI WebSocket, one room per auction (`/ws/auctions/{auction_id}`). Events pushed:
`bidPlaced`, `auctionStarted`, `auctionScheduled`, `auctionExtended`, `auctionFinished`,
`auctionCancelled` — driven by the same domain events, consumed in the API process regardless of
which process (API or worker) originally published them.

## Observability

- **Logs**: structured (`app/core/logging/`), JSON or text (`LOG_FORMAT`), request-id correlated
  across a request via a `ContextVar`.
- **Errors**: Sentry (`SENTRY_DSN`), automatic capture of anything that isn't a handled
  `DomainException`.
- **Metrics**: Prometheus + Grafana, `/metrics` auto-instrumented
  (`prometheus-fastapi-instrumentator`).
- **Traces**: not yet implemented — see `next_steps` roadmap (not versioned; ask the maintainer
  for the current priority list). OpenTelemetry + Jaeger, once added, needs manual trace-context
  propagation through RabbitMQ message headers, since that hop doesn't cross process boundaries
  over HTTP.

## API documentation

Swagger/OpenAPI auto-generated by FastAPI, served at `/docs` (Swagger UI) and `/redoc`.

## Authentication

JWT (access + refresh, `python-jose`), refresh tokens persisted and revocable
(`app/modules/auth/`). Authorization rules live in each router's own dependencies, not in the
auction/bidding domain itself.

## Containerization

`docker-compose.yml` services: `api`, `worker`, `postgres`, `redis`, `rabbitmq`, `mailpit`
(dev SMTP), `prometheus`, `grafana`. One command startup (`docker compose up -d`), local parity
with how the app actually runs.

## Non-goals (explicit)

Kubernetes, service mesh, multi-region, exactly-once delivery, strong consistency across
processes (events are at-least-once; handlers must be idempotent where it matters).

## Evolution path

The module boundaries already exist as if they were service boundaries — extracting one for real
would mean: give it its own database, replace its cross-module *interface* dependency on another
module with a network call (HTTP or async messaging) to that module's own API, and give it its
own auth mechanism for service-to-service calls (see the "microsserviços" discussion — not yet
written up as a doc, ask the maintainer). No business logic rewrite required; that's the entire
point of already routing cross-module communication through events and interfaces instead of
direct calls.

## Engineering principle

> The architecture must protect the domain from infrastructure decisions. If swapping
> infrastructure (in-memory bus → RabbitMQ, being the concrete example so far) breaks domain
> code, the architecture is wrong.
